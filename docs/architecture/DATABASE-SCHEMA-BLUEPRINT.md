## Conventions that apply to every inventory row

- Unless a row says otherwise, PK is `id uuid`, server-generated, with `created_at timestamptz`, `created_by uuid → profiles` nullable only for controlled system/bootstrap activity. Mutable drafts/master records add `updated_at timestamptz`, `version bigint > 0`. Business dates use `date`; event instants `timestamptz`; class time `time`; explicit school timezone `Asia/Kolkata` in configuration. Text is bounded/normalized on input; enums below are checked text domains, not arbitrary strings.
- Every `→ table` is a **foreign key to that table's PK**, with `uuid` type unless the referenced PK is text or composite. All FK columns receive btree indexes unless an existing composite index already covers their left prefix. All U constraints are unique btree indexes. Extra query indexes appear in the last column. Required business fields are NOT NULL; `?` explicitly allows null. Final migration review must enumerate defaults/nullability and avoid surprising nullable uniqueness.
- Default FK deletion rule: RESTRICT. Historical/financial rows never cascade with account deletion. A profile can be disabled and identifying data later redacted under approved retention; domain person and evidence identifiers remain. Pure draft junction deletion may cascade only after review. No public Auth user inventory exposed.
- `CHECK` is for same-row invariants. **Cross-row sums, same-year/subject consistency, valid transitions, overlaps and ownership must be enforced by composite FKs, exclusion constraints, or locked transactional routines/triggers**, not an impossible cross-table CHECK. Every table below inherits append-only or versioned rules from its domain.
- Composite integrity: unique `(id, academic_year_id)` or `(id, section_id)` supporting keys added where dependent rows must reference the same year/section. Do not accept an unrelated section/year/subject just because independent UUID FKs exist. All date ranges are inclusive at business-day level and must be within their parent's year/term where applicable.
- School owns operational records; Auth profile is an actor or authorized viewer, not automatically an unrestricted row owner. Exactly one `school_profile`; **no tenant_id or school subscription tables**. School/year dimensions are not security bypasses.
- Financial amounts use `bigint` paise, currency fixed `char(3)='INR'`, no floating-point. Marks/maximums use `numeric(7,2)`, never money types. Counts/order `smallint` or integer. JSONB is restricted metadata/config snapshots, never a substitute for relationships or unvalidated arbitrary permissions.
- RLS categories below apply to ALL CRUD: CFG configuration, IAM identity/permissions, ST student relationships, HR staff, AC academic assignment, AT attendance, HW homework, EX exam/publication, FI finance, CM communication, DOC documents, JOB operational jobs. Category descriptions and operation-specific rules live in [RLS blueprint](RLS-SECURITY-BLUEPRINT.md). All categories default-deny; no row below implies anonymous access. `P` means selected published subset only.

## Cross-domain integrity gates

Admission numbers are globally unique for this one school, never reused after transfer. A student can have many dated enrollments but no overlapping active placement. Promotion creates a new year enrollment and preserves prior attendance/marks/invoices. Guardian links and teaching assignments have explicit validity; current-role access does not automatically imply access to all historical records.

The same-year and same-student composite keys described above are mandatory, particularly enrollment↔section, marks↔subject exam, invoice↔enrollment, allocation↔invoice/payment, homework↔target enrollment. The ERD omits implementation-support composite columns for readability; it does not relax these constraints.

For every table expose only approved operation paths. Default exposed-schema grants revoked; use a private domain schema plus selected invoker-safe views/RPCs as planned. Audit, role contexts, financial posting, invitations and jobs are never ordinary direct CRUD. Publicly accessible school branding is a narrow deliberate exception, not public school-profile rows.

## Performance plan

Start with indexed relational queries for a single school (planning envelope: 1–5k active students, 5–10 retained academic years; confirm actual scale). No partitioning/materialized views until measured need. FK indexes and unique constraints are correctness requirements, not optional tuning.

Attendance: section/date/session uniqueness, records(session,enrollment), enrollment(student,year), partial pending-correction indexes. Teacher scope: effective assignments and sections indexed. Family scope: guardian+student+validity plus linked profile. Marks: exam/enrollment unique, publication(enrollment,published_at) for family reads. Financial reports: issued_on, settled_at, paid_at and invoice/student/due-date indexes; allocations(payment/invoice,posted_at) support as-of reconstruction.

Paginate with stable keysets `(occurred_at,id)` / `(date,id)` for transaction/audit/history screens. Small catalogs may use bounded offsets. Prefix reference/normalized student identifier search first; trigram/name search only with demonstrated need, query limits and exact authorization. Never search unrestricted student names then filter results in the browser.

Avoid N+1 by returning scoped DTO aggregates in one/few bounded queries, not one query per child/card/month. Authorized views must not bypass RLS; review execution plans under representative user JWT/role context, not only migration owner. Test `EXPLAIN (ANALYZE, BUFFERS)` later on staging synthetic data; no query plans or database benchmarks executed here. Archive closed years via retention/approved cold storage without breaking FK/audit evidence. Any aggregate cache/materialized view must preserve per-caller scope and refresh semantics; default is no shared personal-data cache.

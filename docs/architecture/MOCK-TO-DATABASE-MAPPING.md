# Mock-to-database integration map — proposed

## Step 12 current singleton login scope

Owner-approved initial scope: one Student has at most one active explicitly provisioned login-eligible Parent; one Parent login identity is linked to exactly one Student. Exactly two fields remain for each family role: registration number and its independent six-digit PIN. No Parent Login ID, Guardian Reference/ID, extra username, selection step or third field. Student and Parent have separate internal identities/credentials. Multiple children per Parent and multiple independently login-eligible guardians per Student are **deferred**, while richer non-login guardian relationships remain conceptually supported.

The Step 11 multi-guardian BLOCKED finding is **historical for that earlier scope and remains valid**, not erased or disproven. The new singleton policy removes only that specific selection ambiguity; zero, multiple, inactive, revoked, stale or inconsistent mappings deny. Six-digit production security, provider/Supabase sessions, durable throttling and RLS remain unverified. Only Super Admin provisions/manages grants; five primary roles and immutable audit/finance boundaries remain unchanged.

Current local source updates replace the unused guardianReferenceRequired true flag with false and add pure input/cardinality/evidence-state contracts. The model returns no genuine session and is not wired to routes. Existing public mock dashboards, including the Parent two-child demo, remain unchanged and are not production relationship evidence. Any older instructions to retain the true flag or require a multi-child login mapping below are superseded for this initial phase.

## Migration sequence and data contracts

1. Define shared IDs, year/date semantics and exact money DTOs before replacing imports. UI types currently encode different subject/class enums; map database catalog UUIDs to stable display DTO fields without trusting labels as IDs.
2. Write read-only server adapters with source selection controlled on the server by deployment configuration, never a browser flag that can request real data in demo mode. Keep synthetic fixtures separate and prohibit production seeds.
3. Replace one feature at a time after its domain commands/RLS/positive-negative tests exist. Start roster/calendar, then attendance/homework, published results, and finance. Preserve layout/animations and existing accessible controls.
4. Contract tests compare synthetic DB aggregates to independent expected fixtures. Include no-data vs forbidden vs backend error, not just current successful examples. Add tests for partial page results, cross-year promotion and stale/revoked relationships.
5. Real import is a separate authorized project: explicit source owner, column mapping, duplicate detection, parent relationship verification, trial import into staging, row counts, financial opening balance evidence, exception review and rollback plan. Mock names/reference numbers are never the initial real seed.

## Important semantic decisions

Current student attendance has only present/absent; Parent additionally counts leave in the denominator. Production needs one approved attendance policy for all roles. Unknown/unrecorded sessions must not become absent or be silently excluded. Current academic averages weight by maximum marks; decide absence/exemption/subject weights and published-only aggregate scope. Current reference dates differ (4 Nov learning vs 31 Oct finance), so future date filters must be visible and consistent, not inferred from a greeting clock.

Current Parent fee totals are full-year while Accountant is an independent selected-window ledger. Do not reconcile them by changing numbers to match. Production reconciliation is a query/scope problem addressed by shared invoice/payment facts. Unapplied credit, adjustments, refunds and cross-period settlements require explicit projections, not reuse of the simplified mock formula.

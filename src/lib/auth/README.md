# Local authorization contracts — Step 8

These are pure deterministic **policy evaluators**, not a working authentication system. No route imports them. Existing dashboards are public fictional previews. No Supabase/session client, credential verifier, context constructor, JWT, PIN hash, login endpoint, cookie writer or live user is provided.

`VerifiedServerContext` is a nominal input contract for a FUTURE trusted server adapter. That adapter must verify a real provider session, live account, memberships, tier, MFA, version and DB-bound role context before supplying it. The `source` discriminator and TypeScript brand cannot authenticate an arbitrary object at runtime. Never cast or deserialize client JSON as this type. Recheck these facts and relationships in future RLS/commands; a policy `allowed` result is not a created session or permission grant.

The test script constructs synthetic policy INPUT snapshots in its own scope, without tokens/passwords/PINs and without creating sessions or exposing any route. Successful policy evaluations test assumptions after the future verification boundary; they do not prove provider verification, provenance, SQL RLS or concurrency. No production factory mints these trusted contexts in Step 8.

Ordinary roles require explicit active-membership grants within a ceiling. Only a live Super Admin tier with active Admin context and MFA can manage accounts/roles/credentials or review all five modules. It does not gain an inactive-role union or bypass immutable records/financial checks. Security-change target/approval metadata and record evidence must come from future server lookups, not the request body. Independent approver validity and last-Super-Admin count ultimately require transactional DB checks; this library checks only supplied trusted evidence.

PIN methods are distinct metadata contracts. `credentialBindingMatches` does NOT compare a PIN/hash, resolve a registration number, verify a guardian, or create an Auth session. See [PIN design](../../../docs/architecture/STUDENT-PARENT-PIN-AUTH-DESIGN.md) and [access model](../../../docs/architecture/SUPER-ADMIN-ACCESS-MODEL.md). Do not wire real school data into these public preview pages until authentication, server authorization and RLS are implemented and tested.

## Step 12 local singleton foundation

Current two-field UX: Student registration + six-digit Student PIN; linked Student registration + independent six-digit Parent PIN. No Parent Login ID, guardian reference, extra username or selection step. `guardianReferenceRequired` is now false. Initial login eligibility is one Student to at most one Parent, and each Parent login identity to exactly one Student. Richer non-login guardian records remain conceptually separate; multi-child/multi-login-guardian expansion is deferred. Existing fictional Parent UI still has its original two-child demo and is not this backend model.

`input-contracts.ts` checks transient input format only. Registration is returned unchanged only under an explicitly supplied reviewed school policy; absent policy denies. The ASCII/no-whitespace 128-character ceiling is conservative transport validation, not an invented production school format. Unicode/formats beyond that initial boundary require an explicit policy/contract review. No case folding, PIN trimming or numeric conversion occurs. Do not log full registration identifiers or reflect input in error messages.

`parent-identity.ts` checks cardinality/state/version over a nominal trusted complete lookup snapshot; no lookup implementation exists. Complete forward and reverse login eligibility must eventually be read/validated transactionally. A structural source marker cannot prove school provisioning or lookup authenticity. `resolved_contract` is not authenticated identity.

`authentication-flow.ts` checks ordered assumed evidence, binding attempt, registration, role, profile, provider subject, credential reference/version, session and live context. Provider identity refers to the canonical issuer/subject actually verified for the target session. A future OIDC adapter must separately prove upstream-to-downstream canonical mapping; this library does not conflate an IdP token with a Supabase session. Fresh-login evidence timing is modeled; refresh/continuation requires its own verified lifecycle adapter and live revocation checks.

`contract_access_granted` returns only stage labels and `liveAuthenticationEnabled: false`, no identity/session/token/cookie. It is deliberately incompatible with `AuthenticationResult` and is never wired to a route. `LIVE_AUTHENTICATION_ENABLED` is false. Brands, booleans and source strings are assumed-boundary contracts, not cryptographic verification. Never cast request JSON into them. No public constructor or real provider/limiter/lookup implementation creates trusted evidence. Internal denial categories must map to generic public failures in any future adapter to avoid enumeration.

Run `node verification/verify-auth-foundation.mjs` for Step 12 cases, alongside the original policy and mock-data suites. Format vectors and metadata evidence are synthetic, transient/in-memory and never issued accounts/credentials or usable provider sessions.
